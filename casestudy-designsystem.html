Case Study

⚙️ Scaling an Enterprise Design System Across a Complex Software Landscape

TL;DR

Over two years, I was part of a dedicated taskforce tasked with overhauling and scaling Interhyp Gruppe’s design system. Working hand-in-hand with frontend engineers, we tackled a complex multi-brand environment supporting our parent company, two subsidiaries, and white-label B2B client setups. Beyond foundational elements like custom icons and form controls, I drove the design of complex interaction patterns like step-by-step onboarding, notification centers, and file upload dialogs. The result? Less UI chaos, much faster dev cycles, and a truly cohesive user experience across all products.

Duration: ~2 Years (Ongoing initiative)

The Problem

As our product landscape grew, UI fragmentation increased rapidly. Different teams built similar features in parallel, leading to inconsistent interaction patterns, duplicated development effort, and friction between design and frontend engineering.

The Process

As part of a dedicated taskforce comprising UX designers and frontend engineers, completely overhaul the existing design system, make it scalable, and expand it with missing complex interaction patterns. We designers followed an agile process that can be structured into four discrete steps: Discovery, Define, Design, Hand-off to Frontend Development.

Discovery: Mapping the Chaos

Interhyp Gruppe’s B2B and B2C product suite spans our main company, two subsidiaries, and white-label B2B client environments. Each software team is responsible for certain microservices and the corresponding frontends. As this software landscape evolved, UI fragmentation became a major bottleneck. Product teams were building similar patterns in isolation, resulting in inconsistent user experiences and duplicated frontend effort.

UI Inventory & Brand Audit

We took a deep dive into existing products across all software environments to spot hardcoded styles, messy UI patterns, and redundant components. Major Variables for our subsidiaries and B2B clients included three brand colors (primary, secondary and tertiary), typography, images, and their logo.

Cross-Team Pain Points

Define: Building the Foundation

Before touching any pixels, we needed a rock-solid foundation that could handle both complex component logic and flexible brand scaling without breaking.

Multi-Brand & White-Label Token Architecture

We set up a semantic color token structure that separated UI states from brand identities. This allowed us to easily support distinct CIs for our parent company and subsidiaries, while letting B2B clients inject their own primary, secondary and tertiary brand colors seamlessly.

Scope & Prioritization

We mapped out what we needed: from core building blocks (buttons, form fields, drop-downs) to heavy-duty, stateful patterns (onboarding, notifications, file uploads). To stay organized, we managed our todos in a Kanban board. In our weekly meetings, we reviewed the progress and adjusted priorities as needed. In those discussions, we also identified potential edge cases and developed strategies to address them.

Designing for Different User Groups

We specifically distinguished between two core audiences: professionals (power users) and regular customers. While customers needed an airy, guided, and low-friction experience, professionals required denser UIs to process large amounts of data at a glance and optional keyboard shortcuts.

Strict Layout & Spacing Rules

Our design system was built on a strict 8px grid foundation with predefined spacing tokens. We ensured that this grid was applied consistently across every single component to guarantee visual rhythm and predictability.

System Logic & Edge Cases

We defined component anatomies, responsive behavior, accessibility/contrast rules, and every possible state (default, hover, focus, disabled, error, loading, and overflow text) right from the start. For our icon library, we rebuild a base set of icons with material design iconography and created custom icons only when necessary.

Design: Crafting the Components

Working in iterative loops, I designed and specified a range of components that balanced clean UX with technical reality. The following section highlights some of the components and patterns I designed, along with the challenges we faced and how we solved them.

Notification System

Redesigned our existing inline and pop-up alerts and introduced a centralized Notification Center to catch pop-up messages missed while users were offline. The visual refresh included refined color palettes, tinted shadows (replacing harsh grey ones for a more harmonious look - shoutout to my frontend engineer fellow with whom I co-created those!), and accessible status icons differentiated not just by iconography, but also by distinct frame shapes and colors. For critical warnings and errors, I added action-link buttons offering immediate solutions. Additionally, the system adapts to our two user groups—helping professionals track updates across multiple clients and applications, while keeping regular customers focused on their single application.

Onboarding Dialog

Built upon existing dialog components to create a modular, step-by-step onboarding flow. I integrated a clear progress indicator and designed a flexible user journey allowing users to jump between steps or exit at any time. To maximize focus, the dialogs sit on a semi-transparent backdrop that dims the entire screen except for the exact feature or component being highlighted.

File Upload Center

Our team, the document manager team, was the first to handle file uploads, so I had the opportunity to tackle the file upload as a component. I completely rethought how we handled multiple concurrent files. Previously, uploads were managed via pop-up notifications, which quickly cluttered the screen and caused visual noise when stacking. I designed a centralized Upload Center (which ultimately integrated into our Notification Center) to bundle all active and completed uploads in one clean place.

The upload statuses mirrored our notification system (Success, Info/Uploading, and Error). It was a top priority for me that users always know precisely what went wrong so they can take action—leading to highly detailed error categories (e.g., server errors, unsupported file formats, or corrupted files).

I also split the progress indicator into two distinct phases: the actual file transfer (upload) followed by the background processing phase until the file was fully rendered and ready in the interface. I tried to balance user needs and technical constraints, as users want to know exact remaining time and progress while technically it was possible to provide information about remaining time and data size based on the uploading file chunks. When the file's completely uploaded it wasn't possible to provide details about processing time. As a result, the actual upload was represented by concrete progress information and a grown progress bar and the processing phase was indicated by a indefinite loading animation.

Toolbar

As one of the first components tackled by our team, I defined the toolbar’s entire anatomy from scratch—including spacing, integrated text elements, responsive behavior, and left/right alignment variants. I mapped out dynamic toolbar states depending on user context (e.g., whether associated items are selected or unselected) alongside individual tool icon states, featuring a timed hover delay that triggers tooltips with keyboard shortcuts for power users.

Hand-Off: Bridging Design and Code... and Documentation

A design system is only as good as its adoption. Instead of throwing specs over the fence, we made hand-off a collaborative habit:

Design-to-Code Syncs

We held regular alignment sessions with frontend engineers before final sign-offs to agree on props, tokens, and accessibility details. To close the loop, we also held post-sign-off review meetings to ensure the implementation matched the design intent.

Living Documentation

We wrote clear usage guidelines, "Do’s & Don’ts," and behavioral specs so product teams could grab components and run with them safely across different brands. For the documentation of our design system guidelines, we decided to use Storybook which gave us the flexibility to maintain and update our documentation in real-time.

Outcome

Over the course of three years, our taskforce transformed Interhyp Gruppe’s design system from a collection of isolated UI elements into a scalable, multi-brand architecture. By introducing a robust token setup, we completely eliminated the need to manually restyle interfaces for our parent company, subsidiaries, or custom-branded B2B client portals. Product teams across both B2B and B2C lines could finally rely on pre-tested, flexible building blocks instead of engineering complex flows from scratch.
Ultimately, this initiative proved that a design system is a component library and a strategic foundation that bridges the gap between design and engineering. Through close weekly alignment, and a shared vocabulary, we successfully smoothed out dev hand-offs, eliminated QA bottlenecks, and delivered a truly cohesive user experience at scale.

My Take-Aways

  • Systemic Thinking over Isolated UI: Building a design system is about creating scalable, maintainable architectures that solve real-world fragmentation across a multi-product landscape.
  • The Power of Multi-Brand & White-Labeling: Designing with semantic tokens allowed us to seamlessly scale across our parent company, two subsidiaries, and custom B2B client CIs without duplicating code or design effort.
  • Balancing Different User Needs: Designing for both power users (dense, efficient UIs for professionals) and casual customers (airy, guided experiences) taught me how to adapt system components for different cognitive loads.
  • Design-Dev Collaboration is Everything: A design system only succeeds when design and engineering speak the same language and understand each other's domain demands.
